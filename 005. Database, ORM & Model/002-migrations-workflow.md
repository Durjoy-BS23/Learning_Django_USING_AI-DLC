# Migrations Workflow

## Introduction

You've learned how to create Django models, but here's the catch: **creating a model doesn't automatically create a database table**. That's where migrations come in. Migrations are Django's way of synchronizing your model definitions with your actual database structure. This guide covers the complete migration workflow, from understanding what migrations are to executing them and troubleshooting common issues.

## What Are Migrations?

**Migrations** are Django's system for propagating changes you make to your models into your database schema. Think of migrations as a version control system for your database structure.

### Why Do We Need Migrations?

When you create or modify a model, Django needs to know:
1. What table to create or modify
2. What columns to add, change, or remove
3. What data types to use
4. How to handle existing data

Migrations provide this information in a structured, trackable way.

### When Do You Need to Run Migrations?

You need to run migrations whenever you:
- **Add a new model** - Create a new Python class in models.py
- **Add a new field** - Add a new attribute to an existing model
- **Modify an existing field** - Change field type, max_length, or other options
- **Delete a model** - Remove a model class
- **Delete a field** - Remove an attribute from a model

**Golden Rule:** Run migrations for ANY change to your models, even changes you think don't affect the database. When in doubt, migrate!

## The Migration Workflow

The migration process consists of two main commands:

```
1. python manage.py makemigrations
2. python manage.py migrate
```

### Step 1: makemigrations

The `makemigrations` command examines your models and creates a migration file that describes the changes needed.

```bash
python manage.py makemigrations
```

**What happens:**
1. Django compares your current models with the last known state
2. It detects any changes (new models, new fields, modified fields, etc.)
3. It generates a new migration file in your app's `migrations/` folder
4. The migration file contains Python code describing the changes

**Example output:**
```
Migrations for 'post':
  post/migrations/0001_initial.py
    - Create model Post
```

### Step 2: migrate

The `migrate` command applies the migrations to your database.

```bash
python manage.py migrate
```

**What happens:**
1. Django reads the migration files
2. It translates the migration instructions into SQL
3. It executes the SQL against your database
4. Your database schema is updated to match your models

**Example output:**
```
Operations to perform:
  Apply all migrations: admin, auth, contenttypes, post, sessions
Running migrations:
  Applying post.0001_initial... OK
```

## Understanding Migration Files

Let's look at an actual migration file to understand its structure.

### Example Migration File

```python
# post/migrations/0001_initial.py
from django.db import migrations, models

class Migration(migrations.Migration):

    initial = True  # This is the first migration for this app

    dependencies = [
        # Dependencies on other migrations go here
    ]

    operations = [
        migrations.CreateModel(
            name='Post',
            fields=[
                ('id', models.BigAutoField(auto_created=True, primary_key=True)),
                ('post_title', models.CharField(max_length=60)),
                ('post_content', models.TextField()),
                ('published_date', models.DateTimeField(auto_now=True)),
            ],
        ),
    ]
```

### Migration File Breakdown

**Class Migration(migrations.Migration):**
- The main class that Django looks for
- Inherits from Django's Migration class

**initial = True:**
- Indicates this is the first migration for the app
- Only present on the initial migration

**dependencies:**
- Lists other migrations this one depends on
- Ensures migrations run in the correct order
- Empty for initial migrations

**operations:**
- A list of operations to perform on the database
- Common operations:
  - `CreateModel` - Create a new table
  - `AddField` - Add a new column
  - `AlterField` - Modify an existing column
  - `RemoveField` - Delete a column
  - `DeleteModel` - Delete a table

## Viewing Generated SQL

You can see the SQL that Django will generate from a migration without actually running it:

```bash
python manage.py sqlmigrate <app_name> <migration_number>
```

**Example:**
```bash
python manage.py sqlmigrate post 0001
```

**Example output:**
```sql
BEGIN;
--
-- Create model Post
--
CREATE TABLE "post_post" (
    "id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "post_title" varchar(60) NOT NULL,
    "post_content" text NOT NULL,
    "published_date" datetime NOT NULL
);
COMMIT;
```

This is incredibly useful for:
- Understanding what Django is doing behind the scenes
- Debugging migration issues
- Learning SQL
- Reviewing changes before applying them

## The showmigrations Command

The `showmigrations` command displays which migrations have been applied and which are pending.

```bash
python manage.py showmigrations
```

**Example output:**
```
admin
 [X] 0001_initial
 [X] 0002_logentry_remove_auto_add
 [X] 0003_logentry_add_action_flag_choices
auth
 [X] 0001_initial
 [X] 0002_alter_permission_name_max_length
post
 [X] 0001_initial
 [ ] 0002_alter_post_published_date
```

**Interpretation:**
- `[X]` - Migration has been applied to the database
- `[ ]` - Migration is pending (not yet applied)

This command is perfect for:
- Checking migration status
- Troubleshooting why changes aren't appearing
- Verifying your migration state

## Complete Workflow Example

Let's walk through a complete example of creating a model and running migrations.

### Scenario: Creating a Blog Post Model

**Step 1: Define the Model**

```python
# post/models.py
from django.db import models

class Post(models.Model):
    post_title = models.CharField(max_length=60)
    post_content = models.TextField()
    published_date = models.DateTimeField(auto_now=True)
```

**Step 2: Run makemigrations**

```bash
python manage.py makemigrations
```

**Output:**
```
Migrations for 'post':
  post/migrations/0001_initial.py
    - Create model Post
```

Django created `post/migrations/0001_initial.py` with instructions to create the Post table.

**Step 3: Run migrate**

```bash
python manage.py migrate
```

**Output:**
```
Operations to perform:
  Apply all migrations: admin, auth, contenttypes, post, sessions
Running migrations:
  Applying post.0001_initial... OK
```

The `post_post` table now exists in your database!

### Scenario: Modifying a Field

Now let's say you want to change `published_date` from `DateTimeField` to `DateField` (remove time component).

**Step 1: Modify the Model**

```python
# post/models.py
class Post(models.Model):
    post_title = models.CharField(max_length=60)
    post_content = models.TextField()
    published_date = models.DateField(auto_now=True)  # Changed from DateTimeField
```

**Step 2: Run makemigrations**

```bash
python manage.py makemigrations
```

**Output:**
```
Migrations for 'post':
  post/migrations/0002_alter_post_published_date.py
    - Alter field published_date on post
```

Django created `0002_alter_post_published_date.py` to modify the field.

**Step 3: Run migrate**

```bash
python manage.py migrate
```

**Output:**
```
Operations to perform:
  Apply all migrations: admin, auth, contenttypes, post, sessions
Running migrations:
  Applying post.0002_alter_post_published_date... OK
```

The database column has been updated!

## Re-Migrations

Sometimes you might want to undo migrations and start fresh. Here's how:

### Undoing the Last Migration

```bash
python manage.py migrate <app_name> <previous_migration>
```

**Example:**
```bash
python manage.py migrate post 0001
```

This reverts the database to the state after migration 0001, undoing migration 0002.

### Deleting All Migrations (Development Only)

**Warning:** This will delete all data in your app's tables!

1. Delete all files in your app's `migrations/` folder except `__init__.py`
2. Delete the database file (for SQLite: `db.sqlite3`)
3. Run `python manage.py makemigrations`
4. Run `python manage.py migrate`

This gives you a fresh start with your current model definitions.

## Common Migration Issues & Solutions

### Issue: "No changes detected"

**Problem:** You modified your model but `makemigrations` says no changes detected.

**Possible causes:**
1. You didn't actually change anything
2. You're editing the wrong file
3. Django's migration state is out of sync

**Solutions:**
- Double-check your model file
- Try `python manage.py makemigrations --empty <app_name>` to force a migration
- Check `showmigrations` to see current state

### Issue: "You are trying to add a non-nullable field"

**Problem:** Adding a new field without a default value to a table that already has data.

**Solution:** Provide a default value or make the field nullable:

```python
# Option 1: Provide default
new_field = models.CharField(max_length=100, default='default_value')

# Option 2: Make nullable
new_field = models.CharField(max_length=100, null=True, blank=True)
```

### Issue: Migration conflicts

**Problem:** Multiple developers created migrations with the same number.

**Solution:**
1. Pull the latest changes
2. Rename your migration file to the next available number
3. Run `python manage.py migrate`

### Issue: Database is locked

**Problem:** SQLite database is locked (common during development).

**Solution:**
- Close any database viewers/IDEs
- Stop the development server
- Wait a few seconds
- Try again

## Key Takeaways

- **Migrations** synchronize your models with your database
- **makemigrations** creates migration files based on model changes
- **migrate** applies migrations to the database
- Migration files are stored in your app's `migrations/` folder
- **showmigrations** displays migration status (applied vs pending)
- **sqlmigrate** shows the SQL that will be executed
- Run migrations for ANY model change, even seemingly minor ones
- Migration files describe operations like CreateModel, AddField, AlterField, etc.
- You can undo migrations by migrating to a previous migration number
- Always check `showmigrations` when troubleshooting

## Additional Context & Best Practices

### Never Edit Migration Files Manually

While it's technically possible, editing migration files manually is generally a bad idea because:
- You might break the migration chain
- Other developers won't have your changes
- It's error-prone

**Exception:** Advanced users sometimes edit migrations for complex data migrations, but this is an advanced topic.

### Version Control Your Migrations

Always commit migration files to version control (Git). They're part of your codebase and ensure all developers have the same database schema.

### Migration Files in Production

In production:
- Never delete migration files
- Never modify applied migrations
- Always test migrations on a staging environment first
- Consider using Django's `--fake` option carefully for complex situations

### Understanding Django's Built-in Apps

When you run `migrate`, you'll see migrations for apps you didn't create:
- `admin` - Django admin interface
- `auth` - User authentication system
- `contenttypes` - Content type framework
- `sessions` - Session management

These are pre-installed Django apps that need database tables.

### The Thumb Rule

**Memorize this:** Every time you change a model, run migrations.

Even if you think the change doesn't affect the database (like changing a help text), run migrations. It's better to be safe than to have your database out of sync with your code.

### Exercise 3: Troubleshooting

You run `makemigrations` and get "No changes detected", but you definitely changed your model. What should you check?

<details>
<summary>Solution</summary>

Check:
1. Are you editing the correct `models.py` file?
2. Is your app in `INSTALLED_APPS` in `settings.py`?
3. Did you actually change something (not just add/remove whitespace)?
4. Try `python manage.py makemigrations --verbose` to see what Django is checking
5. Check `showmigrations` to see current migration state
6. Try restarting your development server (sometimes caching issues)

</details>
